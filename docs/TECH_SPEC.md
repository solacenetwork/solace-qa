# SOLACE QA technical specification

## Purpose
A small, application-independent internal observation capture and batch exchange tool. It records evidence, not confirmed defect decisions. GitHub documentation and Monday.com remain the issue-tracking systems.

## Environment and deployment
- Vanilla PHP and JavaScript; Bootstrap 6.0.0-alpha.2 CSS and JavaScript pinned via jsDelivr; native form controls and vanilla JavaScript. The export history page uses the Bootstrap bundle for dismissible alerts. Internet access expected.
- PHP 8.1+; required extensions: `fileinfo` (attachment MIME validation), `zip` (ZipArchive creation and verification), and `intl` (IntlDateFormatter for export and review date display). Verify all three are enabled on the local and hosted PHP runtimes.
- Local: see README.md for private PHP session path and upload limits.
- Hostinger: deploy only contents of public/ into qa.solace.network/public_html/. Preserve hPanel-managed authentication files and HTTPS. Store runtime data in sibling data/; never deploy or overwrite it.
- No database, Composer, npm, application login system or PWA.
- Existing QA records are valuable even during alpha. Preserve valid reports, images and archives. Obsolete disposable development fixtures need no compatibility layer.

## Capture contract (QA-2)
Keep actions, actual and expected behavior, page/workflow, date, report type, suggestion and optional severity. Add project, scenario ID, app version/build, device/model, OS, browser/version, orientation, viewport/screen dimensions, pixel ratio, browser/PWA context, interface mode and reproducibility (always/sometimes/once/not retested). Allow unknown values and manual overrides; reporting environment may differ from tested environment. Remember only reusable environment preferences locally. Add browser compatibility, accessibility, performance and coverage-gap classifications. Classification is preliminary.

Environment detection is explicitly requested by the tester, never silently treated as the target environment. Saved preferences load on return; environment collapses when required saved values are available and expands for invalid hidden fields. Interface mode records the actual tested mode; Automatic selection issues can be described in the observation.  reset clears observation fields while retaining the current environment. Forget removes the saved preferences. Native date input defaults to local today. Existing QA-1 records remain intact; new records use reproducibility rather than the previous repeatable checkbox.

## Persistence and images (QA-3)
Server-generated permanent report UUID. Optional multiple PNG/JPEG/WebP screenshots; validate actual image format, limit count/size, sanitize filename, prevent collisions, retain original quality. Up to five images per report, 10 MiB per image, subject to PHP upload limits. Paths relative to data/ use pics/<report-uuid>-<ordinal>-<safe-name>-<date>.<ext>. The report key is id (UUID v4); images is an array of objects with path, mime and size. Existing records lacking IDs/images are assigned IDs and empty image arrays during the next successful submission, preserving their other fields. Report records contain image associations. Keep storage outside web root. Use data/storage.lock as the one stable lock file for all report/export mutations and atomic same-directory replacement of JSON. QA-2 retains the previous valid JSON generation in submissions.json.bak using atomic replacement before updating the primary. Failed uploads or writes must not commit incomplete observations. Uploaded files are moved before committing JSON and removed on ordinary failure. An abrupt process termination may leave unreferenced files; exports must include only referenced images. Mutating endpoints use POST and CSRF protection.

## Batch exchange (QA-4)
Export only pending reports. ZIP contains manifest.json, submissions.json and associated pics/. Manifest includes format version, generator version, export UUID, ISO 8601 generated time, report/image counts, dataset inventory mapping report UUIDs to image paths, and file inventory with byte sizes and SHA-256 checksums (excluding manifest itself). Hashes verify integrity and identify identical contents, not authenticity. Report UUIDs identify records, export UUIDs identify batches. Do not silently discard distinct reports with identical images. Cross-batch image deduplication may be reported by hash; each archive remains self-contained.
Archive filenames use qa-reports-YYYY-MM-DD-###.zip (local Eastern date, increasing daily sequence). Manifest keys: format_version (1), generator_version (QA-4 or QA-5), export_uuid, generated_at, archive_name, report_count, image_count, checksum_algorithm (sha256), dataset (UUID to array of image paths), files (array of path, size, sha256). History is a JSON list of export_uuid, generated_at, archive_name, report_ids, report_count, image_count, archive_size, archive_sha256 and reviewed_at (null or ISO 8601 review timestamp). Pending status is derived from history, not written into reports. Verify ZIP contents and checksums before marking batch exported. Retain previous archives, allow re-download, and recover safely if interrupted between archive creation and export-state commit. A verified ZIP is atomically renamed from a temporary file before history is atomically replaced. Before selecting pending reports, reconcile any finalized archive absent from history by verifying its contents and checking report IDs and image associations against the stored dataset. Conflicts or missing historical archives stop exports rather than silently resetting history. Temporary archives are not considered committed. Reports without QA-3 IDs must receive IDs through a successful submission before exporting. No report should vanish or enter a later batch accidentally. Maintain export history and separate reviewed status. Archive checksum can be stored in history, outside ZIP. Serve downloads through authenticated PHP with safe path handling.

## Export management (QA-5)
The observation page displays pending and exported report counts and archive count from the reconciled history under the stable storage lock. Zero pending disables the export button; the export endpoint still independently enforces pending selection. If status cannot be loaded, export is disabled and capture remains available. The observation page links to a dedicated export-history.php page; it does not render the archive list. The history page links back to index.php and is also reachable from the export confirmation page. History lists batches newest first with filename, generation time, observation and screenshot counts, download and review state. Both generation and review timestamps are formatted for display using IntlDateFormatter with en_US, LONG date, SHORT time and America/New_York; stored ISO 8601 timestamps remain unchanged. Review is a CSRF-protected POST by export UUID, persists reviewed_at using atomic history replacement under the shared lock, and redirects back to export-history.php. The success alert remains visible across reloads until explicitly dismissed; dismissal removes the review query parameter and fragment with history.replaceState, without repeating the POST. Repeated review requests preserve the first review timestamp. Review is independent of export eligibility; downloads never mark reviewed. No archive deletion or undo-review control is included. Existing QA-4 archives are unchanged, and new archives use generator_version QA-5 with the same format version.

## Hosted acceptance baseline (QA-6)
Hostinger at qa.solace.network uses PHP 8.4 with fileinfo, zip and intl enabled, upload_max_filesize and post_max_size both 256 MB, max_file_uploads 20, and server default timezone UTC. Export/review endpoints explicitly use America/New_York; the history formatter also uses that timezone. HTTPS and HTTP Basic Authentication protect the web root. Only public/ contents are deployed; private data/ is a sibling of public_html/. Preserve authentication and runtime data on redeployment. This is a single-user internal utility; controlled concurrency, interruption and failure simulations remain deferred as recorded in TESTING.md. Do not interpret functional acceptance as a comprehensive security audit.
